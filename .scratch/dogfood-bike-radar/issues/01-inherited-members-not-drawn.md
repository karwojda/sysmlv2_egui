# 01: An Interconnection Diagram drops members inherited from a specialised definition

**Status:** ready-for-agent

**Category:** bug

**Slice:** bike-radar-model slice 2 (commit `b6a3056`), views `partTree` and `internalStructure`.

## Snippet

```sysml
part def RearUnit {
    port radar : RadarPort;          // + rearLight, ble, usbC, mount
}
part def RearUnitDesign :> RearUnit {
    part radarModule : RadarModule;  // + 10 more parts
    bind radar = radarModule.antenna; // + 4 more binds
}
part rearUnit : RearUnitDesign;

view partTree {
    expose rearUnit::**;
    render asTreeDiagram;
}
view internalStructure {
    expose rearUnit;
    render asInterconnectionDiagram;
}
```

## Expected

- **partTree:** `rearUnit` with its 11 parts beneath it, and their ports.
- **internalStructure:** the five boundary ports `rearUnit` inherits from `RearUnit`, each bound to the inner part port that serves it.

OpenSysML's own renderer, `sysml -render 'BikeRadarViews::partTree' -render-form text model`, shows the whole tree. For `internalStructure` it lists the boundary ports and the bindings (`rearUnit.rearLight == leds.light`, …).

## Seen

- **partTree:** one box, `rearUnit:RearUnitDesign`, and nothing beneath it. The result is the same with `expose rearUnit;`, with `expose rearUnit; expose rearUnit::*;`, and with `expose rearUnit::**;`.
- **internalStructure:**
  - The inner parts, their ports and the flows are drawn.
  - The frame has no boundary ports, and none of the five `bind`s appear.
  - So the inner ports `radarModule.antenna`, `leds.light`, `mcu.ble`, `usbCReceptacle.plug` and `clamp.seatpost` all look unconnected.

The members a usage gets through its definition's own specialisation (`RearUnitDesign :> RearUnit`) seem to be dropped. The slice 1 `rideContext` draws `rearUnit : RearUnit`'s ports, which `RearUnit` declares directly, without trouble.

### Triage: split in two

Reproduced with a minimal model: `part def Box { port outer : P; }`, `part def Design :> Box { part inner : Inner; bind outer = inner.p; }`, `part specialised : Design`, with the same members declared directly in a `Plain` def for comparison.

- **Interconnection Diagram:** `plain` draws `outer`, `inner` and the bind. `specialised` draws `inner` only: the inherited port is missing, and the bind, which ends on it, can't resolve and is dropped. That's this ticket.
- **Tree view:** `expose X::**` shows nothing beneath `X` for *both* usages. The tree ignores every member a usage gets from its definition, specialised or not. That's a different cause with a design question attached, and it moves to [05](05-tree-view-ignores-members-from-definition.md).

## Agent Brief

**Category:** bug
**Summary:** An Interconnection Diagram should draw the parts, ports and connections a part definition inherits through specialisation (`:>`), not only those it declares itself.

**Current behavior:**
When the Interconnection Diagram builds a box from a part definition (the Frame of the root, an opened part, or a closed part's ports), it takes only the members the definition owns directly. Members of the definitions it specialises are ignored. For `part def RearUnitDesign :> RearUnit`, the five ports `RearUnit` declares are missing from the Frame of `rearUnit : RearUnitDesign`. Every `bind` or connection that ends on one of them fails to resolve and is silently left out, so the inner ports they serve look unconnected.

**Desired behavior:**
A definition's box shows its own members plus everything it inherits through `specializes`, followed transitively (`C :> B :> A` gets A's members too), for each kind the diagram draws: part usages (children), port usages (on the border), and connections, interfaces, flows and bindings (wires). A connection declared in the specialising definition that ends on an inherited port resolves to that port. A connection declared in a general definition is drawn in the specialising definition's box too.

When the specialising definition declares a member that redefines an inherited one (`port :>> radar`), only the more specific one is drawn. Until the backend records redefinitions, a member with the same name as an inherited one counts as redefining it. A definition reached twice through multiple specialisation contributes its members once.

These members are the **Inherited Members** of `CONTEXT.md`. [05](05-tree-view-ignores-members-from-definition.md) uses the same concept for General Diagrams: build one accessor for both, not one per diagram.

The same applies wherever the diagram shows a definition's members: the Frame, opened parts, and closed parts' ports.

**Key interfaces:**
- `Model` has only `owned_members(owner)`. A way to get an element's members together with its Inherited Members (own first, then nearest definition first, redefined ones hidden) is needed, shared with 05. `Element::specializes` already records the `:>` targets by qualified name.
- The Interconnection Diagram's box building (the Frame, opened boxes, closed boxes' ports) and its wire collection should use it.

**Acceptance criteria:**
- [ ] For `part def Box { port outer : P; }`, `part def Design :> Box { part inner : Inner; bind outer = inner.p; }` and `part specialised : Design`, the Interconnection Diagram of `specialised` draws `outer` on the Frame, `inner` inside it, and the binding between `outer` and `inner.p`.
- [ ] A connection declared in `Box` between two of `Box`'s members is drawn in `Design`'s diagram.
- [ ] With `part def Design2 :> Design`, `Design2`'s diagram draws `Box`'s and `Design`'s members (transitive).
- [ ] A member of `Design` that redefines one of `Box`'s (`port :>> outer`) is drawn once, not twice.
- [ ] A closed part typed by `Design` inside another diagram shows `outer` among its ports.
- [ ] Diagrams of definitions without specialisation are unchanged (existing interconnection golden files still pass).
- [ ] The bike-radar-model `internalStructure` view (slice 2, commit `b6a3056`) shows `rearUnit`'s five boundary ports, each bound to its inner part's port.

**Out of scope:**
- The tree view (`asTreeDiagram`) and General Diagrams: see [05](05-tree-view-ignores-members-from-definition.md).
- Port placement and label overlap: see [04](04-layouts-hard-to-read.md).
- Inheritance between usages (`part a :> b`) and members a port inherits from its port definition's own supertypes, unless they fall out of the same accessor for free.
