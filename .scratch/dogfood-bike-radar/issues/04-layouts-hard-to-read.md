# 04: Port labels overlap on a crowded edge

**Status:** done

**Category:** bug

**Slice:** bike-radar-model slice 1 (`rideContext`, `systemRequirements`) and slice 2 (`internalStructure`), commit `b6a3056`. Pictures: `bike-radar-model/docs/img/{internalStructure,rideContext,systemRequirements}.svg`, exported by `viewer-cli export --all`.

## Expected

An engineer can read each diagram at its natural size without guessing which label belongs to which port or flow, and without scrolling sideways across a page.

### Triage: split into six tickets

The report bundles about eight problems with different causes. Checked against the code:

- **Ports go only on top or bottom, by design.** In the Interconnection Diagram, an `in` port goes on top, an `out` port on the bottom, and a port with no direction faces the other end of its wire with a strong vertical bias, or goes on the bottom when it has nothing wired. Every bike radar port carries items both ways, so none has a direction. Ports on a side are spaced evenly along it with no minimum gap, so labels collide.
- **Child order is lost twice.** The Model keeps elements keyed by qualified name, so declaration order is lost at load. The layered layout then reorders children again.

## Agent Brief

**Category:** bug
**Summary:** In an Interconnection Diagram, port labels on the same edge of a box must not overlap each other or the labels of neighbouring ports.

**Current behavior:**
Ports on one side of a box are spaced evenly along it, however many there are and however long their labels (`name : PortDef`) are. A box sized for its title and children can end up with five port labels on one edge printed on top of each other. Examples from the bike radar: `rearUnit` in `rideContext` (`mount`, `rearLight`, `ble`, `radar`, `usbC` on one edge), and in `internalStructure` `mcu` (three on each edge), `usbCReceptacle`, `ledDriver` and `radarModule`.

**Desired behavior:**
For every side of every box, including the Frame and Opened Parts:
- port labels don't overlap each other;
- they don't overlap the box's title or a child box.

When the ports' labels need more room than the side has, the box grows along that side (and the layout around it adapts). Ports keep the order along the side they have today, and evenly spaced ports with short labels are drawn as they are now. A port moved by the user (a port position in the Layout) is still honoured. If a manual position makes labels collide, that's the user's choice.

**Key interfaces:**
- Interconnection Diagram box sizing and port spreading. The label text is what the diagram draws for a port (`name : Def`, with `~` for conjugated).
- Golden SVGs for interconnection tests, which will change where ports were crowded.

**Acceptance criteria:**
- [ ] A test: a part with five undirected, unconnected ports with labels of realistic length, and no two port label bounding boxes intersect.
- [ ] A test: a box whose own size is smaller than its ports' labels need grows so that its labels fit.
- [ ] bike-radar-model `rideContext` and `internalStructure` (commit `b6a3056`) have no overlapping port labels.
- [ ] Diagrams whose port labels already fit are unchanged (golden files unchanged, or changed only where they had overlap).

**Out of scope:**
- Which side a port goes on: [08](08-ports-only-on-top-and-bottom.md).
- Wire routing and wire labels: [07](07-interconnection-wires-overlap.md).
- Tree and General Diagram layout.
