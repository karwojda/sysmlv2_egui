# 02: A StateTransitionView is not exported or drawn

**Status:** ready-for-human

**Category:** enhancement

**Slice:** bike-radar-model slice 2 (commit `b6a3056`), view `operatingModes`.

## Snippet

```sysml
private import StandardViewDefinitions::*;

view operatingModes : StateTransitionView {
    doc /* Off, and the three modes the button cycles through when on. */
    expose OperatingModes;
}
```

`OperatingModes` is a `state def`: `off`, and a composite `on` with `dayFlash`, `nightSolid` and `radarOnly` inside it, plus six transitions triggered by `accept`.

## Expected

A state machine diagram: states as rounded boxes, the composite `on` holding its three substates, initial pseudostates, and transitions labelled with their trigger.

The standard library has no `asState…` rendering. Typing the view by `StandardViewDefinitions::StateTransitionView` is how SysML v2 asks for one. OpenSysML honours it: `sysml -render 'BikeRadarViews::operatingModes' -render-form text model` reports "state rendering (view def StateTransitionView)" and lists the states and transitions.

## Seen

`export --all` prints `warning: view BikeRadarViews::operatingModes is not Exported: it is a StateTransitionView` and writes no file. The viewer has no state machine rendering at all (it has only `asTreeDiagram` and `asInterconnectionDiagram`), so the operating modes, which are a core part of the architecture slice, can't be shown.

The warning is clear, so this is a missing feature rather than a bug.

## Comments

> *This was generated by AI during triage.*

### Triage: a new Diagram Kind, not an agent task

Confirmed from the code: the viewer has no element kinds for states, state definitions or transitions, so `OperatingModes` and its states are Unsupported Elements, listed only in the Browser. `CONTEXT.md` already anticipates more Diagram Kinds ("Browser, General, or Interconnection (others later)"). No ADR or out-of-scope entry rejects it. The warning works as intended; the feature is missing.

**Why it can't go to an agent yet:** this is a new Diagram Kind with design decisions no one has made:

- how states, composite states, and initial and final pseudostates are drawn under the Standard Notation;
- how a composite state (`on` holding `dayFlash`, `nightSolid`, `radarOnly`) is laid out;
- how transitions are labelled (trigger, guard, effect) and routed;
- what the Layout stores for it;
- whether a `state def` and its states also appear in General Diagrams and the Properties panel.

**Next step:** take it through the main flow, `/grill-with-docs` → `/to-spec` → `/to-tickets`, when it's chosen. The bike-radar-model plan revisits it at the slice 3 stop point, alongside the other findings.
