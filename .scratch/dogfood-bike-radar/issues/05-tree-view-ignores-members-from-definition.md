# 05: A usage's Inherited Members are not shown in General Diagrams

**Status:** done

**Category:** bug

**Slice:** bike-radar-model slice 2 (commit `b6a3056`), view `partTree`. Split out of [01](01-inherited-members-not-drawn.md) during triage.

## Snippet

```sysml
part def Inner { port p : P; }
part def Box { port outer : P; attribute mass; }
part def Design :> Box {
    part inner : Inner;
}
part specialised : Design { part own; }

view tree { expose specialised::**; render asTreeDiagram; }
```

## Expected

`specialised` with its Inherited Members in its compartments, marked `^` (see the brief below). The original report expected the definition's parts as nodes beneath the usage. The grilling chose SysON's form instead: inherited members are compartment rows, never nodes.

## Seen

One box, `specialised:Design`, with no compartments for anything it has through `Design` and `Box`. A Tool-defined General Diagram rooted at `specialised` is empty but for `own`. Everything that reads an element's members uses only what the element declares itself.

## Comments

> *This was generated by AI during triage.*

### Triage notes (superseded by the grilling below)

The first triage asked whether inherited members should become tree nodes, shared or per usage, and how their Layout entries would be keyed. The grilling settled it by following SysON, which makes that question disappear.

### Grilling decisions

SysON (`DiagramQueryToolService.getInheritedCompartmentItems`, `InheritedCompartmentItemNodeDescriptionProvider`) draws inherited features as `'^' + label` rows, in italics, in the owner's compartments. It hides those that a closer feature redefines or subsets, and its "Add existing elements" follows containment only. OpenSysML's `sysml -render` instead walks inherited features as nested tree nodes. Delegating to that is [12](12-resolve-views-through-opensysml-render-view.md), a separate decision.

1. An **Inherited Member** (`CONTEXT.md`) is a member an element has through its definition or a definition it specialises.
2. General Diagrams show it as a `^name : Type` row, in italics, in the `attributes`, `ports` or `parts` compartment of the element that has it. It is never a node of its own.
3. The node set still follows containment. `expose X::*` and `X::**` are unchanged.
4. View exposure, Tool-defined General Diagrams and compartments all change together.
5. A Tool-defined General Diagram rooted at a usage draws the usage itself as its top node, as a requirement root already is.
6. Always shown, no toggle. Standard library members never appear, because library elements aren't in the Model.
7. A member that redefines (`:>>`) an inherited one hides it, with same-name as the fallback while redefinitions aren't recorded. This is the same rule as 01.
8. Rows: declared first, then `^` rows, nearest definition first.

## Agent Brief

**Category:** bug
**Summary:** General Diagrams show the members an element has through its definition and that definition's supertypes as `^` rows in its compartments, and a Tool-defined General Diagram rooted at a usage draws that usage.

**Current behavior:**
Compartments, view exposure and Tool-defined General Diagrams read only the members an element declares itself. A usage typed by a definition (`part rearUnit : RearUnitDesign`) is drawn as an empty box, although `RearUnitDesign` and the `RearUnit` it specialises give it 11 parts, 5 ports and 12 attributes. A Tool-defined General Diagram rooted at such a usage doesn't draw the usage at all, only what it declares itself, which can be nothing.

**Desired behavior:**
- **Rows:** a node's `attributes`, `ports` and `parts` compartments list its Inherited Members as well as its own, in the same row form, prefixed `^` and in italics. In the SVG Export, italics may be `font-style="italic"`.
- **Where they come from:** for a usage, its definition's members and those of every definition that definition specialises, transitively. For a definition, the members of every definition it specialises.
- **Hiding:** a member that redefines an inherited one hides it. Until the backend records redefinitions, a member with the same name as an inherited one hides it. A definition reached twice contributes once.
- **Order:** declared rows first, then inherited rows, nearest definition first.
- **Not nodes:** Inherited Members never become nodes. `expose X::*`, `X::**` and `X::*::**` select nodes by containment exactly as now.
- **Usage roots:** a Tool-defined General Diagram rooted at a usage draws the usage as its top node, with its compartments, and the members it declares below it as today.
- **Inherited asserted constraints** keep their existing `^` marks. Don't show them twice.

**Key interfaces:**
- A Model-level way to get an element's members together with its Inherited Members, using `Element::typed_by` and `Element::specializes`. It is **shared with 01**: one accessor, used by both the Interconnection Diagram and the notation.
- The notation code that builds compartments (`attributes`, `ports`, `parts`).
- The General Diagram builder for a Tool-defined root.
- Golden SVGs whose nodes have definitions with members, which will gain rows.

**Acceptance criteria:**
- [ ] With the snippet above, `specialised`'s node lists `own` as a declared part, `^inner : Inner` under `parts`, `^outer : P` under `ports` and `^mass` under `attributes`, in italics.
- [ ] A test for transitive inheritance: a usage of `C` where `C :> B :> A` shows `A`'s members after `B`'s.
- [ ] A test: a member of `Design` that redefines `Box`'s `mass` hides `^mass`.
- [ ] A Tool-defined General Diagram rooted at `specialised` draws `specialised` with those rows, and `own` below it.
- [ ] `expose specialised::**` draws `specialised` (with rows) and `own`, and no node for `inner`, `outer` or `mass`.
- [ ] A definition node `Design` lists `^outer` and `^mass` from `Box`.
- [ ] Nodes whose definitions add no members are unchanged.

**Out of scope:**
- Drawing Inherited Members as nodes, or per-usage instance trees: see [12](12-resolve-views-through-opensysml-render-view.md).
- A show/hide toggle.
- The Interconnection Diagram: [01](01-inherited-members-not-drawn.md).
- Members from standard library definitions.
