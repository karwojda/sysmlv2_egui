# 12: Resolve views through OpenSysML's `render_view`

**Status:** needs-triage

**Category:** enhancement

**Blocked by:** 06

**Origin:** grilling on [05](05-tree-view-ignores-members-from-definition.md), prompted by [OpenSysML#1212](https://github.com/Open-MBEE/OpenSysML/issues/1212).

## Why

The viewer resolves a `view`'s `expose`s itself. OpenSysML's renderer resolves the same view differently. For `expose specialised;` with `specialised : Design` and `Design :> Box`, `sysml -render … -render-form text` (v0.11) walks the usage's features, inherited ones included, as nested tree nodes (`own`, `inner` with its `p` and `a`, `outer`, `mass`), while the viewer follows containment (and, after 05, shows inherited members as `^` rows). So a view drawn by the viewer and by `sysml -render` can show different things.

The `opensysml` **0.11** client has `Model::render_view`, `render_view_bounded` (depth) and `render_view_folded` (compartment folding: `positioned`, `most`, `ports`). They return a structured `RenderedView`: nodes with `id`, `kind`, `name`, `parent`, `compartment`, `ports` and source `origin`, plus edges and notices. The viewer could ask OpenSysML what a view contains, and only lay it out and draw it.

## What it would bring

- Views drawn the way OpenSysML's own tools draw them.
- OpenSysML's extensions for free, through the same call (#1212):
  - `attribute depth = N` on a view, a SysIDE convention;
  - `filter` applied while walking beneath exposed roots;
  - the renderer's notices ("nested deeper than N levels; not shown").

## Standard SysML or extension

| Mechanism | Status |
|---|---|
| `expose`, `filter`, `render asTreeDiagram` | Standard (Views library) |
| What a tree draws beneath an exposed element | Not specified: OpenSysML walks features, SysON follows containment |
| `filter` while walking beneath roots | OpenSysML extension |
| `attribute depth = N` | SysIDE convention adopted by OpenSysML |
| `DiagramLayout::Layout { collapsed = true }` | OpenSysML library; puts layout in the Model, against ADR 0002 |
| `^` for inherited features | Standard notation (SysON uses it; OpenSysML's text form doesn't) |

### Open questions for triage

- **Layout keys:** `RenderNode.id` is "stable identifier within the rendered view". Is it stable across edits and loads, so it can key Layout entries and Orphaned Layout Entries? This needs a spike.

**Spike (opensysml 0.11.0, `render_view` on bike-radar `internalStructure`):**

- **Layout keys: answered, not stable.** `RenderNode.id` is an ordinal (`n0`, `n1`, `n46`, …). Adding one attribute to `RadarModule` moved every later id by one (`mcu` `n46` → `n47`). Ids can't key Layout entries; a key would have to come from the chain of parent `name`s (`rearUnit` → `radarModule`), close to the viewer's feature paths.
- **Contents differ from the viewer's.** The renderer returns every attribute of `radarModule` and five `assert constraint`s as nodes, plus 35 edges. Taking its answer as is would change what every Model-defined Diagram shows, and most golden files with it.

Still open: scope, what replaces the viewer's own expose logic, fold mode and depth, and the ADR.
