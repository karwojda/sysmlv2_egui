# 03: Nothing shows which OpenSysML version checked the Model

**Status:** ready-for-agent

**Category:** bug

**Slice:** bike-radar-model slice 1 (commit `8a9b194`), `model/requirements.sysml`. Found while writing slice 2.

## Snippet

```sysml
requirement def StakeholderNeed {
    subject unit : RearUnit;
}
requirement riderNeeds : StakeholderNeed {
    doc /* What the rider needs from the rear unit. */
    stakeholder rider : Rider;     // a parameter, before any subject in this usage
    // …
}
```

## Expected

The viewer and `sysml` (OpenSysML CLI) agree on whether the model is valid. Failing that, the viewer says which OpenSysML version it checked the model with, so a disagreement can be explained.

## Seen

- `sysml -validate model` with **v0.11.0** (`~/.local/bin/sysml`) gives `error[subject-parameter-position]: Subject must be first parameter.` on `riderNeeds`, exit 2.
- `viewer-cli check` on the same files reports no problem. It loads, exports and checks all 18 requirements, exit 0.

**Likely cause:** version skew. The viewer starts `sysml-grpc` from `~/.opensysml/bin`, which holds v0.10.0 and v0.10.1, the `opensysml = "0.10.0"` client's pinned binaries. The CLI on PATH is v0.11.0. Nothing in the viewer's output shows which backend version did the checking. The model was fixed (`subject :>> unit;` before the stakeholder) in bike-radar-model `b6a3056`, so reproduce with the slice 1 commit.

## Comments

> *This was generated by AI during triage.*

### Triage: version skew confirmed, split in two

- `Cargo.lock` pins the `opensysml` client at **0.10.0**. With no override, the client downloads the `sysml-grpc` release matching its own crate version, v0.10.0 (`~/.opensysml/bin/sysml-grpc.json`).
- The `sysml` CLI on PATH is **v0.11.0**, which added `subject-parameter-position`.
- Each tool is right for its version. The `sysml` and `sysml-lsp` v0.11 now in `~/.local/bin` don't change what the viewer runs: it uses `sysml-grpc`, not the CLI.
- The service reports its build version in `ServerInfoResponse.version`, reachable from the client as `Connection::capabilities().wire().version`. The viewer never reads it, so a disagreement can't be explained from its output.

Moving to 0.11 is split out to [06](06-move-to-opensysml-0-11.md). This ticket is now about showing the version.

## Agent Brief

**Category:** bug
**Summary:** The viewer and its CLI should say which OpenSysML `sysml-grpc` version loaded and checked the Model.

**Current behavior:**
Neither the GUI nor `check`, `requirements` or `export` mentions the backend version. The version is whatever the `opensysml` client downloads to match its own crate version, unless `--sysml-binary`, `--sysml-service`, `OPENSYSML_GRPC_BINARY` or `OPENSYSML_SERVICE` points somewhere else, and then it can be anything. When the viewer and another OpenSysML tool disagree on a Model, the user can't tell whether that's version skew.

**Desired behavior:**
- **CLI:** every command that loads a Model (`check`, `requirements`, `export`) prints the service's reported version once, on stderr, so that stdout and its exit code stay as they are (for example `OpenSysML sysml-grpc v0.10.0`).
- **GUI:** the version is visible without hunting for it, for example in the status bar or an About panel. The placement is the implementer's choice.
- The version shown is what the running service reports, not the client's crate version, so an override is reported truthfully. A service that reports an empty version or `dev` is shown as such (`dev`, `unknown`), never hidden.

**Key interfaces:**
- `opensysml::Connection::capabilities()` → `Capabilities::wire().version`: the service's build version, informational only.
- The backend's load result (whatever `load_with` returns) or the backend itself needs to carry the version out to the CLI and GUI. It belongs to the backend layer, not the Model.

**Acceptance criteria:**
- [ ] `sysml-viewer check <model>` prints the backend version once on stderr; stdout and the exit code are unchanged.
- [ ] `requirements` and `export` do the same.
- [ ] With `--sysml-binary` pointing at a different release, the printed version is that release's.
- [ ] The GUI shows the version after a load.
- [ ] An empty version from the service is shown as `unknown`.

**Out of scope:**
- Bumping the `opensysml` client: see [06](06-move-to-opensysml-0-11.md).
- Refusing or warning about particular versions, or comparing versions.
- Anything to do with the `sysml` CLI or `sysml-lsp`.
